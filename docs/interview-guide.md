# 面试问答准备

## 为什么选 Vue3 + Spring Boot？

Vue3 适合快速构建中后台和移动端页面，组合式 API、生态和 Vite 开发体验比较稳定。Spring Boot 适合实现结构清晰的后端服务，和 MySQL、Redis、WebSocket、Maven、测试工具集成成熟。这个组合对简历项目来说成本可控、资料多、可维护性好。

## JWT 如何鉴权？

登录成功后后端生成 JWT，前端把 token 放在 `Authorization: Bearer <token>` 请求头中。后端 `JwtInterceptor` 校验 token 签名、过期时间和格式，然后把用户信息写入 `UserContext`。请求结束后清理上下文。

## 为什么需要数据库复核角色？

JWT 是签发时的快照。如果管理员角色被移除，旧 JWT 里仍可能带着 `ADMIN`。所以项目在 HTTP 拦截器和 WebSocket 握手阶段都会重新查询数据库，确认用户状态为 `NORMAL`，并使用数据库中的当前角色做权限判断。

## PBKDF2 和旧密码兼容怎么做？

新注册密码使用 PBKDF2，格式是 `pbkdf2$iterations$salt$hash`。旧密码如果是 64 位 SHA-256 哈希，登录时仍支持校验。旧密码登录成功后，后端会把密码哈希升级为 PBKDF2。

## 如何防止重复报名？

分两层处理：

1. 业务层查询同一活动同一用户是否已经有有效报名。
2. 数据库层使用 `activity_signup(activity_id,user_id)` 唯一约束兜底。

这样即使并发请求同时进入，也会被数据库唯一约束挡住。

## 如何减少并发超员？

不能只在 Java 内存里判断人数，因为并发下多个请求可能同时看到还有名额。项目使用数据库条件更新：

```text
approved_count < max_participants
```

只有更新成功才算抢到名额，失败则返回活动已满的业务错误。

## 候补如何转正？

用户加入候补时，MySQL 保存 `activity_waitlist` 和 `activity_signup` 状态，Redis List 保存候补顺序。有人退出成功报名后，系统先从 Redis `LPOP` 取第一个候补；Redis 不可用或队列为空时，回退 MySQL 查询最早的 `WAITING` 记录。转正时先抢占名额，再把候补改为 `PROMOTED`，报名改为 `APPROVED`，最后发送通知。

## Redis 和数据库如何保持一致？

项目按业务区分一致性要求：

- 验证码只在 Redis 中，过期或删除后不可复用。
- 候补业务以 MySQL 为最终可信状态，Redis 只维护顺序。
- 看板首页概览使用 Redis 缓存，Redis 异常时回退数据库。

目前看板概览依赖 5 分钟 TTL 保证最终一致性，关键业务写入后的主动失效留待后续统一评估。

## WebSocket 如何鉴权？

前端连接：

```text
ws://127.0.0.1:5173/ws?token=<JWT>
```

后端握手拦截器读取 token，校验后重新查询数据库用户状态。消息发送时还会检查用户是否有活动群聊权限，只有活动发起人或 `APPROVED` 报名用户可以发送和接收该活动聊天消息。

## 文件上传如何校验？

`FileUploadUtils` 校验：

- 文件不能为空。
- 扩展名只能是 `jpg`、`jpeg`、`png`、`webp`。
- 读取文件头判断真实图片签名，防止只改扩展名伪造图片。
- 文件大小由 Spring multipart 配置限制。

## 数据看板口径如何定义？

每个指标都明确：

- 名称。
- 业务含义。
- 时间字段。
- 包含状态。
- 排除状态。
- 计算方式。
- 空数据和除零处理。
- 对应接口。

例如报名成功率使用 `activity_signup.created_at`，分子是 `APPROVED`、`PROMOTED`、`COMPLETED`，分母是全部未删除报名记录。

## 为什么只缓存首页概览？

首页概览访问频率高、数据量小、对实时性要求相对低，适合 5 分钟 TTL 缓存。趋势、分布、质量指标和排行受时间范围影响大，参数组合多，缓存收益不稳定，所以保持实时查询，避免缓存复杂度扩大。

## Docker Compose 的作用是什么？

Compose 只管理 MySQL 和 Redis，让本地开发环境更可复现。前端和后端仍在 Windows 本机启动，方便调试。MySQL 和 Redis 使用项目专属容器名、端口和数据卷，避免影响其他项目。

## GitHub Actions 的作用是什么？

当前有两个工作流：

- `ci.yml`：push 和 PR 时运行后端测试、后端打包、前端安装和构建。
- `security-scan.yml`：运行 Gitleaks 扫描可见 Git 历史和当前提交，发现疑似真实密钥时失败。

它们用于防止明显破坏构建和误提交敏感信息。

## 为什么推荐没有使用协同过滤或深度学习？

当前项目没有足够的真实浏览、点击、报名转化和留存数据，训练出来的模型不可靠。Stage 2.8 需要在一周内完成，因此选择可解释、可测试的内容与业务特征加权排序，避免引入 Python 服务、模型训练和额外运维链路。

## 推荐算法如何计算？

先召回最多 100 条未来仍可报名、非本人发布且当前用户未参与的 `SIGNING/FULL` 活动，再计算兴趣 35%、距离 25%、热度 15%、时间 15% 和发起人信用 10%。缺失特征从分子和分母同时移除，最终按分数降序、开始时间升序、活动 ID 升序稳定排序。

## Jaccard 为什么适合当前兴趣匹配？

用户兴趣和活动标签都是小规模集合，Jaccard 可以衡量交集占并集的比例，不依赖训练数据。项目再加入活动覆盖率，避免活动只有少量标签命中时被过度低估；兴趣理由直接展示真实交集标签。

## 没有定位怎么办？

距离特征返回 `null`，不按 0 分处罚，也不进入最终权重分母。系统继续使用兴趣、热度、时间和信用排序。首页只有用户主动点击“使用位置优化”时才请求浏览器定位，拒绝定位会保留原推荐。

## 新用户没有兴趣怎么办？

兴趣特征标记为不可用并动态归一化剩余权重。即使同时没有定位，热度、时间和发起人信用仍可完成冷启动推荐。

## 推荐服务如何避免 N+1？

候选阶段只读取原始 `Activity`，发起人使用 `selectBatchIds` 一次批量查询。评分和排序完成后，只对最多 10 条 Top N 结果调用包含候补、资料、收藏和报名查询的 `ActivityService.toVO()`。

## Redis 挂了会怎样？

缓存读取、JSON 反序列化或写入异常都会记录 warning。读取失败后直接从 MySQL 召回并实时计算，写入失败只影响后续缓存命中，不会让推荐接口返回 500。

## 数据规模变大后如何演进推荐？

先基于真实指标评估权重和召回质量，再考虑离线特征、更多召回通道和可审计实验。当行为数据量、效果收益和运维能力足够时，才评估协同过滤或学习排序；当前规则排序仍可保留为可解释召回和故障降级。

## 项目目前还有哪些不足？

- 尚未公网部署。
- 没有真实支付。
- AA 账单、固定搭子、举报处理仍是预留或基础结构。
- 数据看板主动缓存失效尚未统一接入。
- 依赖审计中还有 `echarts`、`vite`、`esbuild` 的非阻塞风险，需要后续评估大版本升级。
- 管理后台目前以查询和展示为主，缺少更完整的运营处理流程。

## 如果继续优化，你会做什么？

优先级建议：

1. 明确公网部署方案和配置隔离。
2. 清理或禁用演示账号。
3. 给看板写入链路增加统一缓存失效事件。
4. 对 ECharts、Vite、Playwright 做兼容性升级评估。
5. 补全举报处理、AA 账单和固定搭子业务闭环。
6. 增加接口级集成测试和更多 E2E 用例。
